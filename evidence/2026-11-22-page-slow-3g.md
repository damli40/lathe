# The page on a phone over slow 3G, 2026-11-22

Measured before hosting the page. The page was served locally with gzip (as a real host does) and opened in headless Chromium at 360 × 740, with the network throttled to 400 kbit/s down and up and 400 ms latency per request (Chrome's "slow 3G" figures). One run per row.

| | First paint | Headline text | Load event | Requests | Size on the wire |
|---|---|---|---|---|---|
| Before | 1,444 ms | 4,520 ms | 29,890 ms | 296 | 1,291 KB |
| After | 1,560 ms | 3,810 ms | 6,775 ms | 51 | 406 KB |

What changed:

- `VIEM_URL` in `web/config.js` now points at esm.sh's single-file build of viem 2.21.0 (`/es2022/viem.bundle.mjs`, about 77 KB compressed). The plain entry loaded about 280 separate files.
- `web/index.html` preloads the page's own script files, so they download side by side, and opens the connection to the font host early.

Width check at 320, 360, 390 and 768 px: the page is never wider than the screen and no element sticks out. One tap target is under 28 px tall, and the smallest text is 10 px (the labels on the figure).

All page tests pass on this version: 53 unit tests, `e2e`, `readonly`, `fixround`, `memory`, `receipt`, `pieces`, `casegas`, `detect`, `fork`, and `config-live` for both networks.

Tried and removed: a small starter script that filled the page text before the main script arrived. It brought the headline to 1,442 ms, but `web/test/fork.mjs` then failed every time: the test's first click on "Approve" did nothing, and a second click worked. The cause was not found, so the script is not in the page. The headline still waits for the main script.

Not measured: a real phone, a real mobile network, the hosted page (these figures are from a local server), and the Chinese text.
